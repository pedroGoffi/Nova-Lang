# Metaprogramação com annotation processors

Este pacote demonstra metaprogramação tipada executada durante a compilação. Uma `annotation` declara os metadados e onde eles podem ser usados; uma função marcada com `#[processor(...)]` recebe o AST anotado e o transforma.

Execute o exemplo com:

```console
cargo run -- run examples/features/metaprogramming
```

## Declarações principais

```nova
pub annotation Getters() on struct, class;

#[processor(Getters)]
fn add_getters(target: &mut Type, annotation: Getters) -> () {
    // transformação do AST
}
```

- `target` é o tipo anotado. Ele é mutável porque o processador pode adicionar membros e alterar sua declaração antes da análise semântica.
- `annotation` contém os argumentos fornecidos na anotação. Por exemplo, em `@Log(level = "debug")`, `log.level` vale `"debug"`.
- `Type`, `Function` e `Field` vêm de `std::meta` e só existem durante a expansão procedural.
- `Annotation`, `Member`, `Parameter` e `Body` são outras visões disponíveis para ferramentas meta.
- `quote` cria um fragmento de AST tipado. `quote fn nome(...)` cria um membro de função; `quote { ... }` cria corpo ou sequência de statements.
- `${body}` preserva/injeta o corpo original dentro de um quasiquote de função.

Um processor não promete modificar o alvo. Ele pode somente consultar metadados, validar uma regra, alterar um corpo, adicionar membros ou não produzir mudança alguma.

## Visões com `has<T>` e `as<T>`

Todo alvo meta pode ser consultado antes de usar uma visão específica:

```nova
let is_type = target.has::<Type>();
let type_view = target.as::<Type>();
```

- `has::<T>()` informa se o nó oferece a visão `T`.
- `as::<T>()` retorna a visão tipada correspondente.
- `generatedBy::<A>()` consulta se um nó foi emitido por um processor associado à annotation `A`. A proveniência é registrada automaticamente quando o nó é adicionado ao AST e não altera o ABI.
- As visões iniciais são `Type`, `Function`, `Field`, `Annotation`, `Member`, `Parameter` e `Body`.
- Consultar ou converter uma visão não implica chamar `members.add` nem gerar código.

## API de `Type`

| Campo/operação | Significado |
| --- | --- |
| `target.name` | Nome declarado do tipo. |
| `target.fields` | Todos os campos, na ordem da declaração. |
| `target.fields.required` | Campos que não possuem valor padrão. Útil para construtores de argumentos obrigatórios. |
| `target.members.add(member)` | Adiciona ao tipo uma função produzida por `quote fn`. |
| `target.has::<T>()` | Testa se o alvo possui a visão meta `T`. |
| `target.as::<T>()` | Obtém a visão meta `T`. |
| `node.generatedBy::<A>()` | Consulta a annotation responsável por gerar um campo, membro ou outra declaração. |
| `field.type.is::<T>()` | Faz uma checagem de tipo durante a compilação. |

O mesmo processador pode ser aplicado a `struct` e `class` quando ambos aparecem depois de `on`.

## API de `Field`

| Campo | Significado |
| --- | --- |
| `field.name` | Nome do campo, como `logger`. |
| `field.type` | AST do tipo declarado, como `Logger`. |
| `field.type.reference` | AST de referência imutável ao tipo, como `&Logger`. Seu retorno ainda depende das regras de lifetime suportadas pelo ownership checker. |
| `field.default` | Expressão padrão, quando presente. |
| `field.annotations` | Metadados do campo, como `@Inject`. |

As coleções de parâmetros e inicializadores aceitam atribuição por nome:

```nova
constructor.parameters[field.name] = field.type;
constructor.initializer[field.name] = field.name;
```

Isso significa, respectivamente: “adicione um parâmetro com este nome e tipo” e “inicialize este campo usando o parâmetro homônimo”.

## Getters

`@Getters` percorre `target.fields`, cria um template por campo e o adiciona ao tipo:

```nova
for field in target.fields {
    let getter = quote fn get(self: Self) -> () {};
    getter.name = format!("get_{field.name}");
    getter.result = field.type;
    getter.body.wrap(quote {
        io::stdout().write_line("Getter generated by annotation for ${field.name}");
        return self[field.name];
    });
    target.members.add(getter);
}
```

Para `port: i32` em `AppConfig`, o resultado equivale a:

```nova
fn get_port(self: Self) -> i32 {
    return self.port;
}
```

Neste estágio, o getter consome `self`. O ownership checker ainda não carrega a prova de lifetime necessária para retornar com segurança `&self.field`. Quando essa projeção de lifetime for suportada, o mesmo template poderá usar `self: &Self`, `field.type.reference` e `&self[field.name]`.

## Setters

Setters usam exatamente o mesmo modelo de template por campo:

```nova
for field in target.fields {
    let setter = quote fn set(self: &mut Self, value: ()) -> () {};
    setter.name = format!("set_{field.name}");
    setter.parameters["value"] = field.type;
    setter.body.wrap(quote {
        io::stdout().write_line("Setter generated by annotation for ${field.name}");
        self[field.name] = value;
    });
    target.members.add(setter);
}
```

Para `port: i32`, isso gera semanticamente `set_port(self: &mut Self, value: i32)`. O type checker continua verificando chamadas do método gerado; passar uma `str` onde o campo exige `i32` é erro normal de tipos.

## Injeção e construtor

`@Inject` é metadado passivo: ele não instancia dependências. `@RequiredArgsConstructor` gera `new(...)` com os campos obrigatórios, mas o `Logger` continua sendo criado no composition root e passado para `UserService::new(logger, config)`.

Annotation processors não são limitados a construtores ou getters. O modelo é transformação de AST: processadores de função podem envolver corpos; processadores de tipo podem inspecionar campos e produzir membros; anotações de campo podem carregar metadados para essas transformações.

## O parâmetro tipado da annotation

O segundo parâmetro do processor não é apenas um marcador. Ele contém os valores declarados no schema da annotation, incluindo defaults:

```nova
pub annotation Getters(
    prefix: str = "get",
    message: str = "Getter generated by annotation for"
) on struct, class;

#[processor(Getters)]
fn add_getters(target: &mut Type, annotation: Getters) -> () {
    // annotation.prefix e annotation.message são valores tipados disponíveis
    // durante a expansão.
}
```

O uso pode sobrescrever cada argumento:

```nova
@Getters(prefix = "read", message = "Read accessor generated for")
struct AppConfig { port: i32 }
```

Nesse caso, o método produzido chama-se `read_port`, e não `get_port`. Argumentos desconhecidos, duplicados, ausentes ou com forma inválida são diagnosticados durante a expansão.

## Proveniência e checagem de tipo

Proveniência é uma consulta, não uma ordem de geração:

```nova
for field in target.fields {
    let generated = field.generatedBy::<SomeAnnotation>();
    let integer = field.type.is::<i32>();
}
```

Quando um processor adiciona um `Field`, `Member` ou outro nó ao AST, o compilador associa automaticamente a annotation ativa como origem. Processors executados depois podem usar `generatedBy::<A>()` para incluir, ignorar ou tratar esse nó de outra forma.

## Debug declarado em Nova

`Debug` é uma annotation normal do pacote, não um derive embutido:

```nova
pub annotation Debug(name: str = "", pretty: bool = false) on struct, class;

#[processor(Debug)]
fn add_debug(target: &mut Type, debug: Debug) -> () {
    let body = quote {
        let mut formatter = Formatter::debug_struct("${target.name}");
    };

    for field in target.fields {
        body.append(quote {
            formatter.field("${field.name}", self[field.name]);
        });
    }

    body.append(quote { return formatter.finish(); });

    target.members.add(quote fn to_debug_string(self: Self) -> String {
        ${body}
    });
}
```

`Formatter` segue o vocabulário de Rust: `debug_struct`, `field` e `finish`. O processor usa somente fragmentos gerais (`quote`, `append` e `${body}`); não existe um gerador `Debug` especial no compilador. O método produzido implementa o protocolo usado por `{:?}`:

```nova
println!("{:?}", AppConfig::new("debug-demo", 7070));
```
